# Modelagem do Banco de Dados

## 1. Objetivo

Este documento define a estrutura lógica do banco de dados do Sistema de Gestão para Clínica Médica.

A modelagem foi construída para:

- Preservar o histórico clínico dos pacientes;
- evitar duplicidade de dados;
- garantir integridade referencial;
- controlar agendas e conflitos de horários;
- permitir auditoria das operações;
- suportar autenticação e autorização;
- facilitar futuras evoluções;
- manter compatibilidade com PostgreSQL e Spring Data JPA.

---

## 2. Tecnologias

O sistema utilizará:

```text
PostgreSQL
Spring Data JPA
Hibernate
Flyway
```

O PostgreSQL será responsável pelo armazenamento dos dados.

O Spring Data JPA e o Hibernate serão utilizados pelo backend para mapear as entidades Java para as tabelas do banco.

O Flyway será responsável pelo versionamento da estrutura do banco.

---

## 3. Convenções

### 3.1 Tabelas

As tabelas utilizarão:

- Letras minúsculas;
- nomes em português;
- nomes no plural;
- separação com underline.

Exemplos:

```text
usuarios
pacientes
agendamentos
historicos_agendamento
```

### 3.2 Colunas

As colunas utilizarão `snake_case`.

Exemplos:

```text
nome_completo
data_nascimento
criado_em
atualizado_em
```

### 3.3 Chaves primárias

As entidades principais utilizarão:

```sql
BIGINT GENERATED BY DEFAULT AS IDENTITY
```

### 3.4 Datas

| Informação | Tipo |
|---|---|
| Apenas data | `DATE` |
| Apenas horário | `TIME` |
| Data e horário | `TIMESTAMP WITH TIME ZONE` |

### 3.5 Exclusão lógica

Cadastros administrativos utilizarão:

```text
ativo BOOLEAN
```

A desativação deverá ser utilizada no lugar da exclusão física sempre que o registro possuir histórico.

### 3.6 Auditoria

As principais tabelas poderão possuir:

```text
criado_em
criado_por
atualizado_em
atualizado_por
```

# 5. Tabela `usuarios`

## Finalidade

Armazenar as contas utilizadas para acessar o sistema.

## Estrutura

| Campo | Tipo | Obrigatório | Regra |
|---|---|---:|---|
| `id` | `BIGINT` | Sim | Chave primária |
| `nome` | `VARCHAR(150)` | Sim | Nome do usuário |
| `email` | `VARCHAR(180)` | Sim | Valor único |
| `senha` | `VARCHAR(255)` | Sim | Hash da senha |
| `perfil` | `VARCHAR(30)` | Sim | Perfil de acesso |
| `ativo` | `BOOLEAN` | Sim | Padrão `TRUE` |
| `ultimo_login_em` | `TIMESTAMPTZ` | Não | Último acesso |
| `criado_em` | `TIMESTAMPTZ` | Sim | Data de criação |
| `criado_por` | `BIGINT` | Não | Usuário criador |
| `atualizado_em` | `TIMESTAMPTZ` | Não | Última alteração |
| `atualizado_por` | `BIGINT` | Não | Usuário responsável |

## Perfis

```text
ADMIN
RECEPCIONISTA
MEDICO
```

## Constraints

```text
PRIMARY KEY: id
UNIQUE: email
CHECK: perfil em ADMIN, RECEPCIONISTA ou MEDICO
```

## Índices

```text
idx_usuarios_email
idx_usuarios_perfil
idx_usuarios_ativo
```

## Regras

- O e-mail deverá ser armazenado em letras minúsculas.
- A senha deverá ser armazenada com BCrypt.
- A senha nunca deverá ser retornada pela API.
- Usuários inativos não poderão realizar login.
- Usuários com histórico não deverão ser apagados fisicamente.

| `status` | `VARCHAR(20)` | Sim |
| `cancelado_em` | `TIMESTAMPTZ` | Não |
| `motivo_cancelamento` | `VARCHAR(500)` | Não |

## Status

```text
EMITIDO
CANCELADO
```

## Regras

- Apenas o médico responsável poderá emitir.
- A quantidade de dias deverá ser maior que zero.
- O CID será opcional.
- O CID somente aparecerá quando houver autorização.
- Atestados cancelados permanecerão armazenados.
- Atestados emitidos não poderão ser alterados diretamente.

# 23. Integridade referencial

Para registros históricos e clínicos, será utilizado comportamento equivalente a:

```text
ON DELETE RESTRICT
```

Isso impedirá a exclusão de registros que possuam relacionamentos.

Exemplos:

- Paciente com consulta;
- médico com agendamento;
- consulta com receita;
- receita com itens;
- prontuário com alergias.

O uso de:

```text
ON DELETE CASCADE
```

será limitado a situações técnicas específicas.

# 24. Conflitos de agendamento

A validação deverá impedir dois agendamentos ativos para o mesmo médico no mesmo período.

A regra de sobreposição será:

```text
novo_inicio < agendamento_existente_fim
E
novo_fim > agendamento_existente_inicio
```

Status que bloqueiam o horário:

```text
AGENDADO
CONFIRMADO
PACIENTE_PRESENTE
EM_ATENDIMENTO
```

Status que não bloqueiam:

```text
CANCELADO
NAO_COMPARECEU
CONCLUIDO
```

A operação deverá ser executada dentro de uma transação para evitar conflitos simultâneos.

# 30. Decisões do MVP

Para a primeira versão:

- Cada paciente terá um prontuário principal.
- Toda consulta estará vinculada a um agendamento.
- Não haverá módulo financeiro.
- Não haverá cadastro de convênios.
- O atendimento inicial será presencial.
- O sistema atenderá uma única clínica.
- Receitas e atestados dependerão de consultas.
- Dados clínicos não serão apagados.
- Cadastros serão desativados logicamente.
- Operações importantes serão auditadas.
